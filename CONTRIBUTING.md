# Building & contributing

## Prerequisites

- macOS 13+ with [Xcode](https://apps.apple.com/app/xcode/id497799835)
  (command-line tools included)
- An Apple ID added to Xcode (free tier is fine — caveat below)
- Optional, for the test harness and lint checks: Python 3 and Node (both
  usually present on a dev Mac)

## Repository layout

| Path | What |
|---|---|
| `extension/` | **Source of truth** — the web extension (manifest, scripts, icons) |
| `app/MediaKeyGuardForSafari/` | Xcode wrapper project (generated by `safari-web-extension-converter`, then maintained by hand) |
| `harness/` | Standalone HTML page for testing the release mechanism against Safari |
| `tools/` | Icon generator and the resource-sync script |

## Syncing: automatic

The Xcode project holds **copies** of `extension/` under
`app/MediaKeyGuardForSafari/MediaKeyGuardForSafari Extension/Resources/`.
Keeping them current is a build phase — **Sync extension resources**, first
phase of the extension target — which runs `tools/sync-resources.sh` on every
build, before resources are copied. Edit `extension/`, build, done.

The copies are gitignored build artifacts. On a **fresh clone** they don't
exist yet, so Xcode's navigator shows the extension's Resources entries in
red — that's normal, not a broken checkout. The first build's sync phase
creates them and the red clears. Never edit the copies; they're overwritten
(and pruned) on every build.

Run it by hand only when you want the copies refreshed without a build:

```bash
tools/sync-resources.sh
```

The phase needs `ENABLE_USER_SCRIPT_SANDBOXING = NO` on the extension target
(set there, not project-wide) — the script writes to `extension/` and the
Resources mirror, both outside the build directory.

New top-level files in `extension/` still need registering in the Xcode
project (Add Files to the extension target, or follow the existing patterns in
`project.pbxproj`) — the sync copies them, but Xcode won't bundle a file it
has no reference for. New icons inside `extension/images/` need nothing — it's
a folder reference.

## Versioning: one file, `Version.xcconfig`

A Safari web extension carries versions in two worlds: Apple's bundle fields
and the WebExtensions manifest. Three places would show a number, so they're
driven from one:

```
app/MediaKeyGuardForSafari/Version.xcconfig
  MARKETING_VERSION        -> app + appex CFBundleShortVersionString
                           -> extension/manifest.json "version" (stamped by
                              sync-resources.sh, which is why the popup footer
                              agrees with Safari's Extensions list)
  CURRENT_PROJECT_VERSION  -> CFBundleVersion (build number)
```

The xcconfig is assigned at **project** level, so both targets inherit it —
which matters beyond tidiness: App Store Connect rejects an upload whose appex
version differs from its containing app's.

Change the version in that one file and build. Xcode reads it for the plists;
the sync phase stamps it into `manifest.json`.

**Never type a version into a target's General tab.** That writes a
target-level override, which outranks the xcconfig and silently reintroduces
the drift.

Both fields stay numeric — App Store Connect rejects letters, and
`manifest.json` only accepts dot-separated integers, so the sync script
refuses anything else. Betas go through **TestFlight** with the version
unchanged and `CURRENT_PROJECT_VERSION` incremented per upload; "beta" never
belongs in a version string.

## Build & run

1. `git clone https://github.com/GarethBlain/MediaKeyGuardForSafari && cd MediaKeyGuardForSafari`
2. Open `app/MediaKeyGuardForSafari/MediaKeyGuardForSafari.xcodeproj`
3. Both targets → Signing & Capabilities → select your team
4. ⌘R — the wrapper app registers the extension with Safari
5. Safari → Settings → Extensions → enable **Media Key Guard for Safari**
   and grant site access

**Free Apple ID caveat:** without a paid Developer ID, Safari treats the
extension as unsigned — tick **Develop → Allow Unsigned Extensions** (needs
"Show features for web developers" in Safari's Advanced settings). That
setting resets **every time Safari quits**; re-tick it each session. A paid
team's signature makes the extension stick.

## Testing with the harness

The mechanism (releasing Safari's Now Playing claim) can't be unit-tested — it
needs real Safari. `harness/index.html` exercises every variant:

```bash
cd harness && python3 -m http.server 8642
```

Open `http://127.0.0.1:8642/` in Safari — **must be http, not file://**
(content scripts never inject into `file://` pages, so the extension appears
broken there). The page's status bar shows whether the extension injected.
Start music in Spotify/Music first; each test tells you what to expect.

Quick lint before a PR:

```bash
for f in extension/*.js; do node --check "$f"; done
python3 -c "import json; json.load(open('extension/manifest.json'))"
```

## Pull requests

- Keep changes scoped; one concern per PR
- `page.js` runs in every page's main world — it must never throw into the
  host page and must not add observable globals beyond `__mediaKeyGuard`
- Describe how you tested (harness results, real sites)
